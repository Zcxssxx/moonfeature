# OpenFeature behavior profile

**Reviewed against the published OpenFeature specification pages on 2026-10-25. This is an implementation map, not a conformance claim or certification.** Requirements can change; revisit the cited pages before a tagged release.

Status means: **Implemented** = behavior exists and is covered by project tests; **Partial** = a narrower MoonFeature profile or a documented gap; **Not implemented** = absent from this release.

| Area | OpenFeature reference | Status | MoonFeature implementation and evidence |
|---|---|---|---|
| Typed Boolean, Number, String, and structure evaluation | [Flag Evaluation API](https://openfeature.dev/specification/sections/flag-evaluation/) 1.3 | Partial | `Client` supports Boolean, Double, String, and JSON value/details methods. Context is explicit and currently required on the base methods; optional context overloads and integer-specific methods are absent. Root evaluation tests cover all four types and safe type mismatch defaults. |
| No-op behavior, caller defaults, and detailed results | [Flag Evaluation API](https://openfeature.dev/specification/sections/flag-evaluation/) 1.4 | Implemented | No provider returns the supplied default. Details carry flag key, value, variant, reason, metadata, and error information. Provider failures and type mismatches resolve to the default. Covered by `evaluation_test.mbt`. |
| Error code vocabulary and extensible reasons | [Types and Data Structures](https://openfeature.dev/specification/types/) | Partial | `ErrorCode` covers missing flag, type mismatch, invalid context/configuration, provider errors, and hook failures. It omits codes such as `PARSE_ERROR`, `TARGETING_KEY_MISSING`, and `PROVIDER_FATAL`. `ResolutionReason` is a fixed enum and cannot represent arbitrary provider-specific reason strings. |
| Provider resolution, initialization, shutdown, and metadata | [Provider](https://openfeature.dev/specification/sections/providers/) 2.2–2.5 | Implemented | One typed `resolve` method accepts expected type and explicit context. The API initializes before swapping, preserves the previous provider on initialization failure, and shuts down unused instances. `local/provider_test.mbt` covers typed results and defaults; root lifecycle tests cover replacement and shutdown. |
| Provider hooks | [Provider](https://openfeature.dev/specification/sections/providers/) 2.3 | Implemented | Providers may return hooks through `evaluation_hooks`; this path participates in the same tested scope ordering as API, Client, and invocation hooks. |
| Domain bindings and domain-scoped providers | [Provider](https://openfeature.dev/specification/sections/providers/) and [Flag Evaluation API](https://openfeature.dev/specification/sections/flag-evaluation/) | Implemented | Domain-specific provider lookup with default fallback is tested. A domain-scoped provider is restricted to one domain. |
| Targeting key and custom context fields | [Evaluation Context](https://openfeature.dev/specification/sections/evaluation-context/) 3.1 | Partial | Optional targeting key, keyed Boolean/Number/String/JSON attributes, lookup, and context merge are implemented. Datetime attributes and fetching the complete attribute map are absent. |
| Context merge order | [Evaluation Context](https://openfeature.dev/specification/sections/evaluation-context/) 3.2 | Partial | API → Client → invocation → before-hook overlay is implemented and tested. Transaction-context propagation is not included in this synchronous first-release profile. |
| Hook context, hints, hook data, and stage order | [Hooks](https://openfeature.dev/specification/sections/hooks/) 4.1–4.4 | Partial | Hook context exposes key, type, default, and merged evaluation context; hints are passed separately and per-evaluation JSON hook data flows between stages. API, Client, invocation, and Provider registration and stack order are tested. Client/provider metadata is not exposed through `HookContext`; data updates use returned `HookBeforeResult` rather than an in-place mutable object. |
| Hook failures and final details | [Hooks](https://openfeature.dev/specification/sections/hooks/) 4.3–4.4 | Implemented | Before, provider, and after failures produce caller defaults and invoke error/finally stages. Error/finally callback failures are contained, recorded, and do not stop later callbacks in the same stage. Finally callbacks receive the same details returned to the caller. Covered by `hooks_test.mbt`. |
| Provider events and event routing | [Events](https://openfeature.dev/specification/sections/events/) 5.1 | Partial | The Provider contract supports ready, error, configuration-changed, stale, reconciling, and context-changed events. API and Client handlers are routed by current provider/domain binding; event details include provider name, optional message/error code, and changed flags. A provider must emit its own transitions; the SDK does not derive status from events. |
| Typed event-handler registration and event metadata | [Events](https://openfeature.dev/specification/sections/events/) 5.2 and [Types](https://openfeature.dev/specification/types/) | Partial | API and Client can add/remove handlers and handlers receive the event kind in details. Registration is not filtered by event type, and arbitrary event metadata is not modeled. Handler failures are contained and drainable. |
| Flag metadata shape | [Types and Data Structures](https://openfeature.dev/specification/types/) | Partial | Evaluation details preserve provider JSON metadata defensively. OpenFeature metadata is limited to Boolean, String, and Number values; MoonFeature currently permits the wider JSON value set. |

## Project-owned rules provider

The in-memory provider is MoonFeature-specific and is not an OpenFeature requirement. It uses first-match ordered rules, AND-combined equality/existence conditions, and a deterministic percentage bucket. Its cross-target vectors and 0%/100% boundaries are tested in `local/provider_test.mbt`. The documented hash is for reproducible targeting, not security.

## Excluded scope

This first runnable profile is synchronous and in-memory. It does not implement transaction context propagation, asynchronous provider methods, remote providers, provider reconciliation, persistence, a management service, or an operator UI. These exclusions are not claims that OpenFeature omits the corresponding concepts.
